# 10 — Runtime, recovery and storage

Status: **review draft v0.2.0; operational implementation deferred**. Dependencies: [01](01_canonical_objects.md), [02](02_data_and_readiness.md), [04](04_experiment_submission.md), [12](12_data_pipeline_and_storage.md) and prescribed stage specifications. This proposal creates no scheduler, database, scientific result, migration or cleanup process.

## Authority and lifecycle

Experiment intent, operational request, resolved dependencies, attempt, trial, result and validation are different objects. The five-input v0.1.0 submission contract remains unchanged. A submission can be recorded before execution exists; only an actual claimed worker with a durable attempt can produce a running state. Scientific rejection or insufficient data is a preserved result; a disk error is an operational failure.

Proposed operational paths are `storage/catalog/submissions/<request_id>.json`, `storage/catalog/attempts/<attempt_id>/events/<event_id>.json` and `storage/catalog/operations/index.sqlite`. Their full state/event schema and APIs are deferred to the bounded submission implementation. Request idempotency scope is the entire platform instance: identical request ID and content returns the original; same ID with different content conflicts. A new request ID may refer to the same experiment and reuse exact compatible results without inventing a second scientific result. Attempt IDs identify actual executions/retries, not recipes. Signal-library groupings retain explicit attempt IDs as well as scientific result references so unresolved/failed work remains visible without a fabricated result. A trial-result idempotency comparison uses scientific_key, outcome, outcome_reason, metrics, artifact_manifests, lineage and exposure_record; operational provenance is excluded. An identical retry preserves the first immutable result row and appends a new runtime attempt link. Different scientific content under the same ID is a conflict, never an overwrite.

Proposed attempt transitions: `recorded → resolving → ready → running → succeeded|failed|cancelled`. Resolution may report `unresolved` or `blocked`; a new attempt/re-resolution event preserves the previous blocker. A scheduler may only move `ready` to `running` with exclusive claim/lease evidence. Worker loss makes completion unknown until reconciliation; it does not mark success. Stage progress is not authoritative scientific status. Exact heartbeat interval, leases, timeouts, cancellation checkpoints and concurrency limits remain deployment decisions before enabling an executor.

## Durable publication protocol

The [legacy ledger](../../Data/docs/global-trial-ledger.md) provides inspected precedent: immutable JSON compact evidence, separate artifacts, SQLite indexes, and file-before-index recovery. The new proposal retains that separation; the [compact artifact contract](../../Data/docs/compact-trial-artifacts.md) shows how exact shared inputs can support replay without copying every aligned history. Neither source proves current legacy integrity.

1. Resolve all immutable input refs and schemas. Obtain the one local writer lock for the affected catalog; computation may be concurrent, publication is serialized. Lock ownership and stale-lock handling require a proven process/lease protocol; never delete a lock because a timeout alone elapsed.
2. Write new blobs under `storage/temporary/<attempt_id>/`, on the same filesystem as their final destination. Flush and fsync bytes, validate checksum, logical row schema/count/order, and required lineage. Content-addressed publication uses create-if-absent/atomic installation; existing matching bytes are reused, conflicting bytes are corruption. Fsync destination directories after installation.
3. Construct and validate the immutable manifest against installed blobs and exact dependency refs. Install the manifest through a same-directory temporary file and atomic no-clobber publication, then fsync its directory. A manifest is the completion marker; readers never inspect uncommitted staging contents.
4. For a trial bundle, publish its artifact evidence first, then its authoritative trial JSON referencing verified installed artifacts. After a P1 trial is durable, publish its separate immutable admission record under `storage/catalog/admission_ledger/records/<admission_id>.json`; admitted/rejected/unresolved is the P1 decision, not P2 validation. Publish P2 validated/failed/unresolved records separately under the Validation Ledger, preserving originating/evaluation trial and exact validation policy/inputs similarly. Never publish an artifact-available flag before evidence exists.
5. In a SQLite immediate transaction, update derived index rows with authoritative paths and hashes. Commit the index only after file durability. Immutable record contents are never edited to match an index. A record file installed before an index failure remains valid and can be indexed by reconciliation.
6. Append the operational completion event only after verifying the scientific publication. Append signal-library links/projections afterward; a missing projection is recoverable from authoritative records and cannot make a failed trial disappear.

Reader contract: ignore temporary paths; resolve only committed manifest references; verify schemas/checksums/reference identities; use one consistent index snapshot and immutable dependencies per request. A stale/missing index may be rebuilt or fall back to exact record lookup. If index and record conflict, the authoritative record/hash wins for repair, but do not silently return inconsistent results. Catalogs on network filesystems or object stores are unsupported until their separate atomicity/locking protocol is designed. A local SQLite implementation may use WAL for concurrent readers; safe shutdown/backup and actual filesystem durability must be tested, not inferred.

An immutable JSON record is either absent or complete. A later artifact attachment is a new immutable attachment/correction event and a derived index update; it does not rewrite scientific result content. A corrected calculation requires a genuine versioned change to its scientific inputs, policy or implementation, which produces the corresponding new bound identity and an explicit supersession relation. Different result content under unchanged scientific inputs remains a conflict; do not fabricate a result ID/version to legitimize it. Never silently erase a failure or replace evidence under the same ID. A reference/annotation correction does not change the meaning of the original trial.

## Failure and recovery matrix

| Interruption or fault | Required visible behavior and repair |
| --- | --- |
| Crash while writing staging blob | No published manifest; trial remains incomplete/failed operationally. Preserve staging until ownership/recovery investigation; no automatic age-based deletion. |
| Blobs installed, manifest absent | Blobs are unreferenced candidates; retry can reuse verified hashes. Do not report a completed materialization. |
| Manifest installed, record/index absent | Reconcile immutable manifest, complete identical deterministic publication and append recovery evidence. No recalculation is required solely to repair indexing. |
| Trial record installed, SQLite commit missing | Re-index the exact record with hash verification; query visibility resumes without mutating the result. |
| Artifact or upstream dependency missing/corrupt | Exact replay unavailable/blocked, not ready; preserve compact result and report the broken ref. Quarantine/access block is operational metadata, not rewritten science. |
| Two publishers, same immutable ID/content | Single winner; loser verifies existing bytes and returns idempotently. |
| Same immutable ID, different semantic content | Hard identity conflict; preserve existing record, reject incoming content and retain diagnostic evidence. |
| Worker lost after scientific commit | Reconcile durable result before retry. Preserve attempt history; never duplicate the scientific result because the worker acknowledgement was lost. |
| Changed policy, code, input snapshot or membership | Create new bound identities and invalidate only affected readiness/descendants. Historical results and their original meaning remain available. Later policy approval/revocation is append-only lifecycle evidence outside the immutable policy definition; never mutate a definition approval marker to determine current eligibility. |
| Signal projection outdated | Rebuild links from authoritative relationship/trial/admission/validation records; do not independently recalculate metrics. |

## Storage and retention

Exact scientific paths, payload addressing, schema entries and proposed Parquet representation are in [12](12_data_pipeline_and_storage.md). Small immutable JSON records are authority. SQLite indexes are query aids; operational coordination tables may contain unrebuildable state, so not every SQLite file is disposable. Definitions remain one authoritative recipe source. Full histories are shared immutable inputs, not copied into every trial artifact. Artifact manifests retain unique detailed evidence and exact reconstruction refs; absence of unique rows is allowed only when the versioned evidence contract guarantees deterministic replay with all dependencies retained.

`storage/cache/` holds accelerators explicitly proven reconstructible. `storage/logs/` holds operational diagnostics, not scientific truth. `storage/temporary/` holds unpublished work with an owner and recovery state. No time-to-live, retention duration, deletion job or guaranteed free-space estimate is defined here. Catalogs, payloads, raw evidence, failures, invalid trials, research-period exposure, lineage and required code/environment refs are retained by default. The existing [inventory](../docs/storage_inventory.md) remains the only measured space report: overlaps and hard links prevent naïve summation or a reclaimable-byte guarantee.

Future backup must capture immutable dependencies plus the authoritative record set and operational state consistently, retain checksums, and demonstrate a restore to a separate root without altering scientific identity. Backup destination, encryption/access policy, retention, recovery-point/time objectives and responsible writer/operator are unresolved. Initial local deployment must explicitly choose them before claiming durable production service. No external transfers or backup writes are authorized by this design document alone.

## Acceptance criteria and gates

The later implementation must test duplicate/conflicting request IDs, competing publication, process termination at every publication boundary, index rebuild from immutable evidence, unreadable/corrupted/missing blobs, disk-full behavior, interrupted late attachments, relocation with matching hashes, stale worker reconciliation and affected-only invalidation. Preserve failed attempts and scientific failures separately throughout. Test deterministic shared-history reuse across multiple asset/horizon trials and full signal-library results including failures. These are implementation acceptance tests, not tests executed by this specification task.

Launch gate: persistent submission and versioned lookup may ship without engines if statuses remain truthful. Real computation additionally requires approved scientific definitions, verified read-only input adapters, readiness and exposure enforcement, safe writer/publication behavior, and one bounded replay comparison. Legacy cleanup or migration remains a separate reviewed action after dependency closure, writer/snapshot verification and restore/replay evidence. No automatic cleanup is scheduled.
