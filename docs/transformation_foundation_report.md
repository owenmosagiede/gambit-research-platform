## Behavior and intentional version 2 changes

Recipes execute exactly the declared single-source ordered transformations. There
is no hidden differencing, imputation, resampling, candidate generation or interaction.
At each historical cutoff, the engine resolves only then-available vintages.
Emitted-history composition uses earlier values calculated at their own event
cutoffs. Release shock uses those historical changes, not revised replacements.

The engine enforces partition isolation, semantic/unit compatibility, explicit
cadence and regular-period gaps, finite arithmetic, parameter domains and pinned
policies. Native release steps require their actual anchor and explicit revision/
event capabilities. Canonical intermediate envelopes and final envelopes preserve
validity/reasons, availability precision, recipe references and lineage closure.
All-null output is `no_valid_output`; unexpected execution defects remain visible.

Version 2 intentionally accepts descriptive zero SD and defined zero numerators
when denominators are nonzero, rejects insufficient parameter configurations,
enforces declared positive-price domains and improves failure propagation. EW
standardization uses a stable centered-variance recurrence. Legacy identities,
versions, implementation hashes and every registration's compatibility mapping
remain recorded; these changes do not redefine an old version.

Feature/Signal logical identity reuses the existing 0.2 recipe digest and remains
stable as observations are appended. Materialization identity distinguishes input
evidence, exact output coverage, implementation and policies. Date-aware transient
results use an explicitly tagged `transformation_execution.1.0.0` profile, preserving
the existing UTC production-manifest identity convention. No transient execution
result is presented as a published production Feature store record.
