November 13, 2026 · production observed at 6:58 a.m. Pacific (14:58 UTC) · USD

## Decision

| Question | Answer |
| --- | --- |
| What limits throughput today? | One executor prepares and verifies inputs for one request at a time. In the latest 40 TS momentum completions, preparation and aligned input loading occupied **87%** of attempt wall time. Event-history replay and periodic intake lock waits also consume material time. P1 and P2 statistics together used **under 0.3%**. |
| What is the smallest worthwhile change? | Give job execution and intake a verified per-request event-history path, and shorten the global writer lock around intake. Keep the current worker count for the first release. Target **at least 15% less end-to-end time** on a representative replay before rollout. Then reduce redundant lineage and source verification. |
| Can the current machine run useful parallel work? | Probably two ordinary TS requests for a bounded trial after scheduler changes. It has two shared vCPUs and 4 GiB RAM, with the second core already serving intake and background work. Start the trial with two TS slots and one heavy CS slot *instead of* two TS slots when a heavy CS request is active. Four workers on this host have no demonstrated benefit and little operating headroom. |
| Should Gambit upgrade? | Keep the current machine while building and measuring the software changes. If two slots sustain a gain and the machine runs short of CPU or memory headroom, use **Basic Regular, 4 shared vCPUs / 8 GiB**, initially with two slots. Use **4 dedicated vCPUs / 8 GiB** only if a matched test shows shared CPU variability or missed service deadlines justify the cost. |
| What improvement was measured? | Recent production throughput was **3.90 requests/hour**, with a **13.9-minute median**. An isolated five-member fixture on the audit Mac completed the same four jobs **1.89×** as fast with two processes and **3.07×** with four. These processes had separate stores and more available cores. Gambit’s production speedup is still a projection. |
| Do this before the rest of FX? | Develop the targeted changes while momentum runs. Restore dependable backups first and prepare the next FX programs in parallel. Apply the optimization at the first compatible cutover or before the next major FX batch. Leave a broader multi-host build for when the next programs or asset classes demonstrate a need. |

A request covers one recipe, one instrument or universe, and one expected direction. Each request can generate multiple horizon-specific P1 and P2 trial records. Throughput and cost below count **completed requests**, including research that runs successfully and rejects the hypothesis.

## 3. Execution and safe parallelism

1. **Intake.** `submit` takes the global research writer lock while freezing the plan, verifying implementation and identity, resolving input metadata, checking duplicates and installing the journal, envelope and initial event. UUID retries and equivalent scientific requests resolve to the canonical record. The intake script’s staged manifest is distinct from accepted submissions. Moving read-only work before the lock would require revalidating exact configuration, catalog/source witnesses, implementation and migration marker inside the lock before writing. [Submit and receipt](../src/runtime/research_jobs.py#L315-L414), [scientific identity](../src/runtime/experiment_identity.py)
2. **Ownership and claiming.** One systemd service holds `research-worker-service`, and its execution thread holds a global `research-executor` lock while replaying and processing the pending list in order. `_pending` reconciles durable journals and returns active work, including interrupted requests. There is no per-job lease, expiry, or fencing token. The one-second service heartbeat reports one active request and becomes stale after 15 seconds. A heartbeat is a liveness signal. Kernel lock ownership prevents a second executor. [Service ownership and heartbeat](../src/services/research_worker.py#L85-L127), [pending and executor loop](../src/runtime/research_jobs.py#L448-L518), [live activity](../src/api/live_activity.py#L22-L76)
3. **Progress, admission, and recovery.** Status changes use hashed append-only attempt events plus a replaceable job projection. Cancellation checks occur during preparation and between phases/horizons. SIGTERM drains the in-flight request. Failed, cancelled, or blocked work requires explicit resume, which creates a new attempt with original inputs and implementation compatibility. An abruptly interrupted active request is recoverable from its event history and existing verified trial artifacts. Recovery may repeat unfinished work but must preserve a single scientific result and its exposure history. The thread supervisor has bounded retries, and systemd restarts a failed service under its own limits. [Event chain and progress](../src/runtime/research_jobs.py#L177-L229), [event publication](../src/runtime/research_jobs.py#L301-L328), [cancel and resume](../src/runtime/research_jobs.py#L416-L447), [trial reuse and exposure](../src/runtime/research_jobs.py#L536-L582), [service drain](../src/services/research_worker.py#L46-L83)
4. **Publication.** Research payloads, trial and relationship records have immutable content-derived identities. Unique temporary files, fsync, atomic replace for mutable projections, and atomic link plus byte comparison for immutable records guard file writes. This provides per-file atomicity. The sequence across payloads, exposure, trial and links still needs recovery. Feature publication has a second global lock, with the packed-lineage index lock acquired afterward. Locator generation changes can invalidate read witnesses or trigger SQLite rebuilds. Running two unmodified executors either leaves one unable to work or, if locks were removed, risks duplicate claims, stale attempts overwriting projections, duplicate Feature preparation, orphaned publication and repeated lineage invalidation. The web projection database is independently rebuilt and swapped. [File commits and artifact closure](../src/research/store.py#L32-L110), [Feature writer](../src/data/feature_store.py#L256-L263), [Feature commit ordering](../src/data/fx_feature_store.py#L192-L255), [packed index transaction](../src/data/lineage_packs.py#L287-L351), [read model](../src/read_model/projector.py#L60-L103)

| Work unit | How to use it |
| --- | --- |
| A complete frozen request | **First production unit to parallelize.** Distinct requests can calculate in separate processes with bounded slots. Keep one coordinator for claims, terminal states, and publication. Preserve selection rules and intake ordering. |
| Recipes and TS instruments | Different recipe × pair requests are independent. Same-pair jobs frequently share price and target pins. Group or prefetch compatible inputs internally only when it leaves the frozen queue and experiment boundaries intact. |
| CS universes and instruments | Separate universe requests can run independently. Member-wise Feature preparation is eligible for later parallel work. A date’s CS ranks, completeness rules, and historical inference need the full frozen member set together. Gather and sort canonically before evaluating. |
| Horizons and time chunks | Horizons can have independent P1 calculations and admitted P2 evaluations after their inputs are ready. Parallelizing this first would duplicate verification and target work for a kernel that takes seconds. Chronological warmup and recursive transforms need the exact causal prefix. Arbitrary date sharding risks changing values, admission, or lineage. The 63D split has a different phase boundary. |
| Multiple machines | Defer. Use read-only, checksummed input bundles and isolated local scratch if eventually justified. Keep the publisher on one host. Each remote result carries request, attempt and fencing generation, input digests and real implementation reference. A worker returns proposed bytes and dependencies for independent verification. Avoid concurrent mounts or a shared filesystem used as an implicit distributed lock service. |

**Proposed local architecture.** Retain one supervisor and one queue authority. The coordinator claims the next request under a short writer transaction and persists owner session, request/attempt ID, monotonically increasing fencing generation, and status. Run one or two subprocesses with private per-attempt temporary directories. They verify inputs and compute candidate outputs. Keep phase access/exposure journaled before reads, commit all P1 admission decisions before authorizing that request’s P2 loads, and use the existing Feature publisher and research store for serialized, verified commits. First pilot can serialize Feature publication and any locator rebuild through the coordinator while workers compute other chunks. Do not hold the global writer lock while a subprocess calculates or performs bulk I/O. Recheck the owning generation under the writer lock immediately before every authoritative commit. A dead child may be reclaimed after exit is verified, with idempotent closure checks for already committed work. Use process ownership and heartbeats for a local pool. Introduce expiring leases with the same fencing only for remote workers. Cancellation stops work at bounded checkpoints, drain stops new claims and finishes all in-flight attempts, and the UI should show the active set. A two-slot implementation also needs intake to recognize multiple active requests and backup/release to drain the coordinator, not one PID alone.

Use one native math thread per process initially if future NumPy/BLAS code is introduced. Keep the total runnable threads below the CPU budget, including projectors. The current worker’s Python code gains little from thread pools for CPU-bound preparation. A process pool is appropriate. A library thread setting alone has little effect today.

There were no research submissions, stress loads, cache flushes, file copies, or benchmarks on production. Production measurements came from existing diagnostics and passive observation.

**Process count.** Each row used the same four fresh executions over independent fixture stores: two positive and two negative five-day change requests, a five-member CS fixture, 434 synthetic source weekdays, five legacy horizons, real Feature/Target verification and artifacts, and mocked provider admission. **Bounds and interpretation.**

- Recent attempt CPU was 808s on average. If service reservations leave 1.5–1.7 usable cores for research, the CPU-only ceiling at that work per request is about **6.7–7.6/h**. The reservation is a scenario. Host background CPU and I/O vary, so two processes could fall short of that ceiling. Four processes on two vCPUs cannot lift it. Target at least one full core of equivalent headroom for shared services on a 4-vCPU plan during heavy intake, paper windows and backups.
- For a concurrent design, assume a **10–25% serialized fraction** until the shorter lock and publisher are measured. The recent writer wait was about 10% and event replay about 17%, with overlap. Those figures motivate the range and do not directly measure the redesigned serialized fraction. Amdahl’s law, `1 / (s + (1 - s) / n)`, gives idealized **1.60–1.82× for two** and **2.29–3.08× for four** before CPU, RAM, I/O and intake limits. The current executor serializes complete requests, so applying that formula to extra copies of today’s worker would be invalid.
- At the moment, accepted waiting work gives a buffer of roughly 545. Sustained admission tops out at **7.5 requests/hour** by the eight-minute minimum, even with spare queue slots. Once the buffer is consumed, rates above this require a bounded, cheaper intake path. At the snapshot, admission of 1,650 remaining roster entries at that maximum takes at least about **9.2 days**. An unchanged intake path would cap fast options at about that time even if their workers can finish sooner.
- The fastest simple hardware change for one unchanged worker would be faster individual cores or reduced shared-CPU steal. If the CPU work were 20% faster and the other 12.2% of recent wall time stayed fixed, the total speedup would be roughly **1.17×**. This is a sensitivity calculation. Additional vCPUs on the unchanged single-worker implementation chiefly give the projector, intake and backup more room. They do not execute additional research requests. More RAM helps with page cache, concurrent processes and future larger inputs. More storage matters now for backup staging and growth. Neither a larger cache nor a faster disk has a measured end-to-end production speedup here.

## 7. Implementation sequence, verification and rollback

1. **Preserve the running work.** Keep momentum and paper trading operating. Under a separate instruction, restore off-host backup staging capacity or qualify a verified snapshot-based staging design. Measure current staging requirement, file count, disk growth and successful restore. The normal deployment is idle-only. The frozen-program path also requires complete intake and a drained executor, with an exact reviewed proposal. A partial-intake bridge would be a separate compatibility feature with evidence for accepted IDs, original plans, pending staged IDs, reservations and pacing cursor. Bypassing the existing complete-intake check would risk relabeling or orphaning work. [Cutover conditions](../deploy/program_cutover.py#L124-L147), [release procedure](../deploy/RELEASE_WORKFLOW.md#L56-L96)
2. **Ship the smallest optimization once qualified.** Target `src/runtime/research_jobs.py` event replay and writer lock sections, `src/runtime/experiment_identity.py` intake dedupe, and timing in `src/research/performance.py`. Measure queue wait separately from exclusive stage durations, lock wait and hold, event-index repair, per-attempt memory, FS read/write and disk latency. The event index is disposable and rebuilds from canonical history. Gate release on at least **15%** improvement in median end-to-end TS replay across representative paired cases, no regression greater than **10%** on heavier P2/CS cases, and no increase in historical-integrity blind spots. If replay alone misses the gate, prioritize exact lineage verification improvements in `src/data/verified_inputs.py`, `src/data/fx_feature_store.py`, and `src/data/lineage_packs.py`.
3. **Benchmark on isolated Linux before any production pool.** Compare serial baseline, reuse-only, and 1/2/4 processes on verified fixtures, first with independent stores and then the actual candidate coordinator and one shared publisher. Use a 2-vCPU/4-GiB configuration for 1 and 2 slots and a 4-vCPU/8-GiB host for 1, 2 and a bounded four-slot stress case. Include long and short TS histories, no-P2 and P2-admitted work, cold new processes, warm existing artifacts, one full CS universe and one value/carry-like point-in-time fixture. Use at least three paired repetitions per condition and a bounded 30–60 minute overlap/soak for the shortlisted configuration, adding repetitions for variance. Log unique requests/hour, p50/p90, CPU by core, steal, RSS and cgroup peaks, available RAM, disk wait/utilization, writer hold/wait and storage growth. Include representative web reads and simulated paper refresh/entry alongside backup staging. Increase the soak duration before full production use if it cannot cover the representative mix.
4. **Prove science and recovery.** Require byte-equal aligned rows, nulls, eligibility, ordering, periods, metrics, P1 admissions and P2 decisions, artifacts, sample digests and lineage under the same environment, with exact equality for deterministic values. This proposal changes scheduling and caching, so it has no justification for numerical tolerance. A reviewed executor change can legitimately alter implementation-derived IDs and manifests. Compare through a verified one-to-one mapping of those references only, retaining original authorities and actual implementation provenance. Preserve future stochastic seeds from canonical trial identity, independent of worker or finish order. Test duplicate claims, both positive and negative phases, corrupt inputs, missing events, stale index, conflicting publication, cancelled and failed workers, killing a child before and after commit, interrupted Feature/lineage publication, retry, drain, and restart. A rejected or incompatible attempt must never reach P2. The benchmark’s exact scientific closure and release approval are separate gates. [Existing equivalence approach](FROZEN_PROGRAM_PERFORMANCE.md), [implementation fingerprint](../src/runtime/research_jobs.py#L22-L30), [frozen compatibility](../src/runtime/execution_compatibility.py#L277-L339)
5. **Authorize a canary, then choose hardware.** Extend `src/services/research_worker.py` and `src/api/live_activity.py` to handle multiple active claims, and update backup/release coordination and paced intake before enabling two slots. On the current VM, proceed only if two slots give at least **25%** more completed requests/hour than the optimized single slot, no memory throttling or OOM, at least **1 GiB available RAM** through the representative mix, and no missed paper window or material web latency regression. Measure those operational baselines before setting exact latency thresholds. When the host cannot meet the gates, use the 4-vCPU/8-GiB Basic plan, two slots first. Scale further only with evidence from the upcoming programs.
6. **Rollback by draining and reducing slots.** Stop new claims, wait for admitted in-flight work to finish or reconcile its attempt, then return to one slot. Keep all frozen submissions, append-only events, exposed phases, verified artifacts and committed results. Rebuild any derived index from authoritative records. Use the reviewed code rollback/compatibility procedure if needed, and verify each preserved request remains runnable with an authorized implementation. Never replace newer research with an older store snapshot. Confirm worker heartbeat, queue continuity, website access, paper schedule and verified backup after the change.
