# Catalog preflight and obsolete preparation retirement

Run `tools/migrate_fx_currency.py --root ROOT catalog-preflight --release RELEASE.json --retire-preparation RETIREMENT.json --output REPORT.json` while web and worker remain available. The output must be outside ROOT. This command uses the same catalog selection and queue checks as the offline planner, without numerical replay, locks, maintenance mode, registry changes, or deletion. It validates the live one-second `worker_service.json` heartbeat separately before and after the scan: exact healthy/idle schema, fresh timestamp, live PID, same worker session, no errors, diagnostics or unknown fields. This one explicitly reported projection may change; offline planning/apply still hash-pin it. Submissions, attempts, batch state and all other files remain in the immutable scan. It compares that catalog inventory again at completion; concurrent catalog changes are a blocker, not a passing result. Exit status 2 means blockers remain. A preflight report cannot be applied.

The retirement request has schema `obsolete_momentum_preparation_retirement_v1`, prefix `storage/catalog/operations/momentum-preparation-2026-10-17/`, an explicitly reviewed `files` mapping of relative paths to `{sha256, bytes}`, and `bundle_sha256`. That digest is the canonical hash of the filename-to-hash mapping for the original three frozen inputs. Keep production requests and reports outside this source repository. Do not generate a fresh request automatically when the reviewed inventory differs.

The list-shaped instrument and scope tables remain byte-identical during planning. Their nested references, scopes, and payload references are indexed; row IDs never become ownership IDs. Unrecognized lists, scalar roots, and malformed table rows fail with their file path.

Retirement requires the exact bundle inventory and internally consistent frozen inputs/programs, paused or completed preparation with no research execution, no active or scheduled preparer, and no external catalog/config/log reference to the bundle's paths, file hashes, input digest, or program IDs. The runtime check also covers related systemd timers/drop-ins and Linux processes. The backup service's exact instruction to stop the old preparer is an exclusion rather than a data dependency. An unverifiable runtime blocks retirement.

Only the named bundle files are added to the deletion candidate. Their outgoing references do not authorize deletion of published Features, Targets, single-pair data, or research results. Preparation payload references are excluded from payload deletion candidates. Existing legacy-CS deletion and retained-TS reconciliation rules remain unchanged; all 43 TS definitions and memberships remain protected.

## Release gate

1. Pass synthetic release checks, review and merge the source change, and build the official release using the existing workflow.
2. Run the candidate catalog-only diagnostic on production through an isolated, read-only source overlay if needed before code deployment. Keep its report, exact source hashes, retirement request, and before/after service health evidence outside the application catalog. No deployment or maintenance window is needed for this diagnostic.
3. Explain and resolve every blocker. A clear diagnostic is a point-in-time result, not an authorization or a substitute for fresh offline checks.
4. In the existing controlled migration window, use `plan` or `resume-plan` with the same `--retire-preparation` request. Catalog selection now runs before numerical replay; catalog blockers prevent replay. Do not silently refresh the bundle inventory. For the separately installed controller, place the reviewed file at `ATTEMPT/preparation-retirement.json` and pin its file SHA-256 as `preparation_retirement_sha256` in `attempt.json`. The controller rejects unpinned or changed inputs before stopping services, and forwards the pinned request. Install the reviewed controller through its separate deployment procedure. An old call without the option safely blocks on retained preparation references.
5. Review the full offline manifest and its digest. Normal apply rechecks the full plan (including scientific validation), exact bytes, inactive preparation runtime, and writer locks. Recovery continues to use the same pinned retirement request. Verify retained data and the activated seven-CS/43-TS catalog through the existing recovery and verification workflow.

The online diagnostic does not stop, disable, or change any service. Before an actual retirement, keep the obsolete preparer and its timer inactive throughout the offline window; do not restart them afterward. No automatic numerical retry is triggered by a successful diagnostic.
